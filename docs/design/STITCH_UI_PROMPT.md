## 1. 品牌與產品背景

### 品牌名稱
- 中文：**玄機堂擇日舘**
- 英文／羅馬字不需要作為主視覺重點。

### 產品目標
1. 讓第一次到訪者快速知道有什麼服務。
2. 讓使用者能用「人生事件」理解自己該選哪一項服務。
3. 用清楚流程、人工確認與費用事前說明建立信任。
4. 導向「開始預約」並送出**預約申請**。

### 產品邊界（絕對遵守）
- 不做自動算吉日、八字、沖煞、方位或唯一日期推薦。
- 不寫「保證結果」、「一定大吉」、「神準」、「立即改運」等內容。
- 專業判斷一律由老師人工確認。
- 表單送出不等於正式預約成功；文案必須是「預約申請已送出」。
- 不做購物車、完整服務費一次付清或電商式 Checkout UI。
- 預約表單送出時不付款；老師人工確認服務內容、總價與日期／時間後，才進入綠界預約訂金付款階段。
- 預約訂金只使用三種級距：服務總價 NT$5,000 以下收 NT$800、NT$5,001～8,000 收 NT$1,200、NT$8,001 以上收 NT$1,600；尾款為服務總價扣除已付訂金。
- 付款階段不是第 5 個表單步驟，應在 4-Step 預約申請完成後獨立呈現。
- 不假造老師年資、傳承、證照、館址、客戶評價、客戶案例或真人照片。

### Logo
請使用真實 Logo，並依背景選擇版本：

## 2. 目標使用者與設計感受

### 主要使用者
- 正在安排結婚、訂婚／文定等婚嫁日程的人。
- 正在處理新生兒命狀或命名的人。
- 正在安排搬家、入宅、神明或祖先相關事宜的人。
- 有住家／空間到場諮詢需求，或不確定服務分類的人。

### 使用者當下需要被回答的問題
- 玄機堂提供什麼服務？
- 我的情況要選哪一個服務？
- 網站會不會直接自動幫我算？（答案：不會，由老師人工確認）
- 價格怎麼看？到場或外縣市怎麼處理？
- 送出表單後接下來會發生什麼？

### 設計情緒
- Calm、Trustworthy、Thoughtful、Grounded
- Taiwanese cultural but contemporary
- 像一間被好好整理過、可安心詢問的傳統服務工作室
- 不要神祕壓迫感，也不要娛樂化或科技算命感

## 3. 視覺設計方向

### 色彩
建立低彩度、紙感的色彩系統。建議起點如下，實際可微調但維持比例：

| Token | 建議色彩 | 使用方向 |
|---|---|---|
| Paper / Base | `#F6F1E7` | 主背景、紙張感底色 |
| Warm Surface | `#EEE5D6` | 卡片／區塊底色 |
| Ink / Primary Text | `#29241F` | 標題、主文字、深色 Header |
| Tea Brown | `#6B5542` | 次要標題、icon、細節 |
| Vermilion Accent | `#9E4B3D` | 主要 CTA、重點標記；少量使用 |
| Muted Gold | `#B48A4A` | 細線、編號、小型 accent；極少量 |
| Sage / Calm Neutral | `#8A9385` | 次要狀態、柔和圖形點綴 |

- 朱紅只用於主要 CTA、重要狀態和極小面積重點。
- 金色只作細節，絕不可大面積亮金。
- 深墨色可用於 Hero 或 Footer，但版面需有呼吸感。

### 字體與排版
- 標題：選擇可讀、帶文化感的明體／宋體風格繁中字體，例如 Noto Serif TC / Source Han Serif TC。
- 內文、表單、按鈕：Noto Sans TC 或同等高可讀現代繁中字體。
- 不要全站使用書法字。
- Desktop 主標約 52–64 px；Mobile 主標約 34–40 px。
- 內文 Desktop 16–18 px，Mobile 16 px；行高寬鬆。
- 使用明確 8pt spacing system，區塊留白大方。

### 圖像與裝飾
- 可以使用非常低干擾的紙張紋理、墨色暈染、窗格、印章感小圓點、細緻格線、抽象山形／屋脊／紙張層次等文化意象。
- 不要使用大量八卦、符咒、發光法陣、財神、香火煙霧、滿版宮廟或遊戲化神祕特效。
- 未取得真實素材前，不生成或暗示真實的老師、店面、客戶或服務紀錄照片。MVP Demo 可生成「示意人物」與「示範個案」視覺，但畫面中需可見標示，且不可使用真實姓名、五星評價、傳承／年資或店面證據來包裝。
- Hero 可使用抽象紙藝／墨色／建築線條／安靜物件的 editorial graphic；也可使用不宣稱真實性的 Demo 裝飾視覺。

### 元件語言
- Cards：偏紙張般的暖色平面、細緻邊框、輕微陰影或內陰影，圓角約 16–20 px。
- Button：俐落、可辨識，不要過度圓潤玩具感；Primary 為朱紅實心，Secondary 為深墨／透明邊框。
- Icon：簡約細線 icon，使用一致筆畫；可帶一點印章或節氣感，但不寫實迷信符號。
- 表單：清楚欄位標題、必填標示、輔助文字、錯誤狀態與選擇狀態。

## 5. 服務架構與內容層級

首頁服務不以大量專業術語分類；請先以人生事件與使用者情境呈現。

### 首頁七張服務卡

| 層級 | 服務名稱 | 簡短說明（可直接使用） | 圖像方向 |
|---|---|---|---|
| Primary | 婚嫁擇日 | 為結婚、訂婚與重要婚嫁安排，先整理需求，再由老師人工確認。 | 雙喜紙藝、紅線、成對留白意象；克制使用紅色 |
| Primary | 新生兒命狀・命名 | 迎接新生兒的重要安排，依實際需求與資料由老師說明。 | 柔和宣紙、圓形印記、襁褓抽象幾何 |
| Primary | 入宅・搬遷擇日 | 為搬家、入宅與入住新居安排合適的辦理時間。 | 屋脊、門框、搬遷紙箱的抽象線條 |
| Secondary | 神明・祖先事宜 | 神明、祖先牌位遷移或祭拜相關需求，可先說明情況。 | 安靜祭桌／線香的極抽象符號，不使用宗教照片 |
| Secondary | 宅事・到場諮詢 | 針對住宅或空間需求，由老師確認是否適合到場安排。 | 空間平面、門窗、位置標記抽象圖 |
| Tertiary | 其他擇日需求 | 不確定該選哪項服務？先描述需求，由老師協助確認。 | 開放的圓形、對話框、方向指引 |
| Tertiary | 其他服務諮詢 | 需求不屬於主要分類時，可先說明想了解的服務方向，由老師人工確認。 | 開放的圓形、對話框、方向指引；不可與其他擇日需求做成相同文案 |

### 服務卡固定結構
- 層級／小標（如「人生重要安排」）
- 服務名稱
- 1–2 句白話摘要
- 一行保守提醒，例如「實際服務內容與提供方式於案件確認時說明」
- CTA：查看服務內容

不要把七張卡全部做成一模一樣的權重。Primary 三張較明顯；Secondary 兩張次之；兩張 Tertiary「其他」卡是較安靜的承接入口，但必須清楚區分「其他擇日需求」與「其他服務諮詢」。

## 6. 歷史生成紀錄｜Batch A 核心畫面（不再重新產出）

請使用同一套 Header、Footer、CTA、Service Card、Trust Card、FAQ Accordion、Form Field 與 Stepper 元件。

### A1｜首頁 Desktop（1440 px）

#### 目標
讓使用者在一頁內完成：理解服務 → 找到情境 → 建立信任 → 了解流程與價格 → 開始預約。

#### 區塊順序（不可更動主線）

1. **Header**
   - Sticky 或 scroll 後變為緊湊版。
   - 主要 CTA「開始預約」保持可見。

2. **Hero**
   - Eyebrow：`人工確認・依需求安排`
   - H1：`為重要時刻，先把日子安排妥當。`
   - Supporting copy：`婚嫁、入宅、新生兒與傳統禮俗相關需求，由老師依實際情況人工確認與安排。`
   - Primary CTA：`開始預約`
   - Secondary CTA：`了解服務`
   - 一句界線提示：`網站不自動產生擇日結果，實際服務以人工確認為準。`
   - 右側或背景採抽象文化圖形；不要使用假的老師照片。

3. **Trust Introduction（四項服務原則）**
   - 區標：`把每一件事，先說清楚。`
   - 四張精緻小卡：
     - 老師人工確認
     - 費用事前說明
     - 依實際需求安排
     - LINE／電話人工聯繫

4. **Services**
   - 標題：`從您正在準備的事開始`
   - 副標：`先選擇最接近的情境；細節會在後續由老師協助確認。`
   - 3 張 Primary 卡（可採 3-column）＋ 2 張 Secondary 卡＋ 1 張「其他」承接卡。

5. **How It Works**
   - 標題：`預約流程很簡單`
   - 預約表單 4 steps：
     1. 選擇服務與需求
     2. 填寫希望辦理期間與基本資料
     3. 填寫聯絡方式與到場需求
     4. 檢查資料並送出預約申請
   - 表單送出後另有後續流程：老師人工確認服務與總價 → 依級距支付預約訂金 → 顯示尾款明細 → 依事前約定收取尾款。
   - 需明確區分「預約申請」、「訂金已付款」與「正式預約／案件成立」。

6. **Pricing Preview**
   - 標題：`價格先有方向，細節再一起確認`
   - 婚嫁擇日卡：`參考區間 NT$1,500～2,500`，必須加小字 `MVP 參考資訊，非正式固定價目。`
   - 神明・祖先事宜：`NT$8,000 起` + `起始參考價格，實際依案件內容與服務範圍確認。`
   - 其他服務：使用「依個案確認」或「服務方向待人工確認」，不可自行補上其他固定金額。
   - 規則：`服務內容、費用與付款方式將於正式確認案件時說明，並依雙方事前約定辦理。`
   - 訂金說明：`老師確認服務總價後，預約訂金依級距為 NT$800、NT$1,200 或 NT$1,600；尾款將於付款成功後列明。`
   - CTA：`查看價格說明`

7. **On-site Service / Service Area**
   - 標題：`需要到場的安排，先由老師確認`
   - 說明：入宅／搬遷、神明／祖先、宅事／到場諮詢可能需要到場。
   - 保守文案：`宜蘭縣內與外縣市的實際服務範圍、交通與費用，將依案件需求確認。`
   - 使用地圖感抽象圖或地點標籤，不放未確認地址。

8. **About / Trust Preview**
   - 標題：`不急著下結論，先把事情了解清楚。`
   - 內容只放已確認的工作方式，不寫老師姓名、年資、傳承、館址。
   - 可以預留「真實招牌／場館照片」圖片框，標記為 `Real asset placeholder — 僅於取得授權後替換`。

9. **FAQ Preview**
   - 4 個 accordion：
     - `網站會直接幫我選出日子嗎？`
     - `送出表單後，算是預約成功嗎？`
     - `外縣市或需要到場，費用怎麼計算？`
     - `資料還沒準備齊，可以先申請嗎？`
   - 文案需保守、直接、白話。

10. **Final CTA**
    - H2：`先把需求告訴我們，後續由老師與您確認。`
    - Primary：`開始預約`
    - Secondary：`LINE 詢問`、`電話詢問`

11. **Footer**
    - 品牌名稱、導覽、服務類別、LINE／電話 placeholder、資料使用說明入口。
    - 不顯示未確認地址、營業時間或社群帳號。

   - 神明／祖先相關特殊案件
   - 時間較急的需求
   - 文案：`以上情況將由老師依實際需求確認服務範圍與費用，不進行網站自動計價。`
4. Pricing Process（6 steps）
   - 提出需求 → 老師確認內容與總價 → 說明訂金與尾款 → 雙方確認安排 → 支付預約訂金 → 完成服務並依事前約定收取尾款
5. Pricing FAQ
   - 表單送出時需要付款嗎？（不需要；先建立預約申請。）
   - 訂金怎麼計算？（服務總價確認後，依 NT$800／1,200／1,600 級距判斷。）
   - 付款後還有尾款嗎？（有，服務總價扣除已付訂金後會列明。）
   - 外縣市／到場費用怎麼確認？
   - 改期怎麼處理？
   - 回答不得寫死未確認規則。
6. CTA：`開始預約`

不要把價格頁做成購物商城、金色價目表或未經人工確認就能立即付款的介面。可呈現訂金級距規則，但不可自動替使用者決定服務總價。

### A4｜預約申請 Desktop（1440 px）

#### 頁面目的
降低填表壓力，清楚說明這是「預約申請」，不是直接成功預約。使用 4-step stepper，最好支援上一頁／下一步、欄位驗證、review 與 submitted state。

#### 頁首
- Breadcrumb：`首頁 / 開始預約`
- H1：`開始預約`
- Intro：`先填寫基本需求；老師確認資料與服務內容後，會透過 LINE 或電話與您聯繫。`
- 明確小提示：`送出後為「預約申請已送出」，不代表正式預約已成立。`

#### Stepper
- 01 您的需求
- 02 服務相關資料
- 03 聯絡與到場
- 04 確認並送出

#### Step 1｜您的需求
- 服務類型（必填；卡片／radio）
- 婚嫁子需求（僅當選婚嫁時顯示）：結婚／訂婚・文定／其他婚嫁需求／不確定，希望老師協助確認
- 希望辦理方式（必填）：單一希望日期／可接受日期區間／有候選日期／尚未確定，希望老師協助
- 希望辦理日期／期間（必填）
- 時間較急（選填 toggle）：`時間較急，希望老師確認是否可承接`
- 需求簡述（必填 textarea）

#### Step 2｜服務相關資料
使用 Progressive Disclosure；不要出現其他服務的欄位。所有專業欄位加上 `可選填，資料不足時老師將再與您確認。`

- 婚嫁：新人姓名、出生年月日、出生時間、國曆／農曆（候選選填欄位）
- 新生兒命狀：新生兒姓名（若已有）、性別、出生年月日時、國曆／農曆
- 新生兒命名：姓氏、性別、出生年月日時、喜歡的字／避免的字（選填）
- 入宅／搬遷：舊址（若適用）、新址、希望搬遷期間、是否涉及神明／祖先
- 神明／祖先：神明相關／祖先牌位相關／搬家・入宅相關／其他／不確定，希望老師協助確認；原所在地、新所在地（若有）
- 宅事・到場：空間／住宅需求簡述
- 其他：自由文字描述
- 其他服務諮詢：希望了解的服務方向與需求簡述

#### Step 3｜聯絡與到場
共同欄位：
- 聯絡人姓名（必填）
- 手機號碼（必填）
- LINE ID（選填）
- 希望聯絡方式（必填）：LINE／電話／皆可
- 方便聯絡時間（選填）：上午／下午／晚上／皆可／其他
- 所在縣市（必填）

到場條件欄位：只在入宅／搬遷、神明／祖先、宅事／到場，或使用者選擇需要到場時顯示。
- 是否希望老師親自到場
- 縣市／地區（必填）
- 詳細地址（選填，提示可於人工確認後補充）
- 是否涉及多個地點（選填）
- 是否方便協助接送老師（選填）
- 到場補充說明（選填）

#### Step 4｜確認並送出
- 使用乾淨的 Review Card 顯示：服務、希望辦理期間、需求、聯絡方式、所在縣市、到場需求。
- 可返回修改每一段。
- 資料使用區塊：
  - Link：`資料使用說明`
  - Required checkbox：`我已閱讀資料使用說明，並同意本次填寫資料供玄機堂擇日舘進行預約聯繫、服務確認及相關溝通使用。`
  - Privacy contact entry：`如需查詢、更正或申請刪除資料，請透過聯絡方式與我們聯繫。`
- CTA：`送出預約申請`
- 次要按鈕：`返回修改`

#### Submitted State（必須設計）
- 圖示：安靜的確認符號，不要彩帶或「成功付款」感。
- H1：`預約申請已送出`
- 內文：`老師將確認您提供的資料與服務需求，並透過 LINE 或電話與您聯繫。`
- 補充：`正式服務內容、費用與安排，將於人工確認後說明。`
- CTA：`返回首頁`、`查看服務內容`

#### Error State（至少做設計規格）
- 若送出失敗：保留已填資料，顯示重試按鈕及 LINE／電話替代聯繫方式。
- 文案：`目前無法送出申請，請稍後再試，或改用 LINE／電話與我們聯繫。`

#### 後續付款階段（不是第 5 個表單步驟）
- 在老師人工確認服務內容、服務總價與日期／時間後，才顯示付款入口。
- 顯示付款摘要：服務名稱、服務總價、預約訂金、付款後尾款。
- 訂金級距只允許：`NT$800`、`NT$1,200`、`NT$1,600`。
- 交易按鈕文案使用：`支付預約訂金`，不可寫成 `支付全部費用` 或 `立即預約成功`。
- 付款成功狀態顯示：`預約訂金付款成功`，並列出服務總價、已付訂金與尾款。
- 若日期／時間尚未完成確認，仍顯示人工確認提醒，不得逕稱正式預約成立。
- 付款失敗／取消狀態需保留案件資料，提供重新付款或 LINE／電話聯繫入口。

## 9. 文案與內容限制

### 可直接使用的保守文案
- `實際服務內容與提供方式於案件確認時說明。`
- `服務內容、費用與付款方式將於正式確認案件時說明，並依雙方事前約定辦理。`
- `老師確認服務總價後，預約訂金依級距收取；付款後尾款明細會一併說明。`
- `實際處理時間會依服務內容、資料完整度與老師安排而有所不同，確認案件時將一併說明。`
- `若需求或資料需要修改，請盡早與老師聯繫；是否需要重新處理或調整費用，將依實際案件確認。`
- `預約申請送出後，老師將確認您提供的資料與服務需求，並透過 LINE 或電話與您聯繫。`

### 不可自行補上的內容
- 正式價格（婚嫁以外）
- 固定完成天數、24 小時回覆、當日回覆或「儘快」等 SLA
- 未確認的付款方式、退款／取消／改期規則與尾款收取方式；已確認的預約訂金級距可依 Spec 呈現
- 老師姓名、資歷、傳承、證照、成立年份、館址、電話、LINE ID
- 真實客戶案例、五星評價、照片證明
- 紙本、PDF、LINE 電子檔、固定幾個名字或固定幾個日期等交付承諾

### Placeholder 格式
對於未確認資料，使用明確 placeholder，不要假內容：
- `<老師正式稱謂待補>`
- `<LINE 帳號待補>`
- `<電話待補>`
- `<真實招牌／場館素材待授權>`
- `<資料使用說明頁待完成>`

## 12. 既有 Spec 規則完整對照（Stitch 必須遵守）

本節把前期需求訪談、Spec、Booking、Pricing、Content 與 Domain Rules 中，會影響 UI 的規則集中列出。若本節與任何示意文案有衝突，以本節的狀態與限制為準。

### A. Confirmed｜必須畫進 UI 的規則

| 規則 | UI 落點 |
|---|---|
| 網站核心是服務介紹＋信任建立＋預約轉換 | 首頁主線、服務卡、Trust、流程與 CTA 必須完整存在 |
| 專業判斷由老師人工確認 | Hero、Trust、FAQ、Booking submitted state 都要說清楚 |
| 使用者從人生事件找到服務分類 | 首頁服務用白話情境，不先丟專業術語 |
| 七項主要服務分類固定 | Header／首頁／服務頁／Booking 選項名稱必須一致 |
| Primary CTA 是「開始預約」 | Header、Hero、服務卡、價格頁、FAQ、Footer 都導向 `/booking` |
| LINE／電話是 Secondary Contact | 不把 LINE 或電話設為唯一主流程；保留並列入口與 placeholder |
| 表單送出是 Booking Request | 不得顯示「預約成功」或「已成立」 |
| 正式預約須經人工確認 | 流程圖與 submitted state 都需呈現人工確認、確認費用、確認安排 |
| 首次送出只收最低基本資料 | 只將姓名、手機、服務、需求、希望日期／期間、縣市、聯絡偏好列為必填 |
| 專業資料採條件式與選填 | Step 2 依服務顯示；不可一次塞入所有命理／宅事欄位 |
| Event Date 與 Contact Preference 分開 | 「希望辦理日期／期間」不得做成老師可預約時段；方便聯絡時間只能是偏好 |
| 到場欄位條件顯示 | 入宅／搬遷、神明／祖先、宅事優先顯示；婚嫁與新生兒不預設到場 |
| 不做電商式付款流程 | 不得出現購物車、完整服務費一次付清或付款倒數；綠界預約訂金只能在人工確認總價後出現 |
| 預約訂金採三段級距 | 服務總價 5,000 以下收 800；5,001～8,000 收 1,200；8,001 以上收 1,600；付款後顯示尾款 |
| 價格為混合式揭露 | 價格卡需能呈現參考區間、依個案確認、特殊人工報價三種狀態 |
| 外縣市、到場、多地點與特殊案件不自動計價 | 不設公里計算器、即時總價或自動加價 UI |
| 費用原則於服務前說明 | Pricing／流程／FAQ 中需保留「確認案件時說明」 |
| 急件只是需求訊號 | 可有選項，但不可承諾優先、保證承接或固定急件費 |
| 改期／修改依案件進度人工確認 | 不建立自助免費改期或固定改期費功能 |
| Trust 只用可驗證真實資料 | 無素材時使用真實服務原則與 placeholder，不用假見證 |
| 資料使用同意必須存在 | Booking Step 4 必須有 Notice Link、Privacy Contact Entry 與 Required Checkbox |

### B. Proxy Assumption｜可用於版型，但不可寫成老師已確認的事實

| 暫定方向 | Stitch 呈現方式 |
|---|---|
| 婚嫁首頁維持一張主卡 | 詳情／表單中可再選結婚、訂婚／文定、其他或不確定 |
| 婚嫁 NT$1,500～2,500 | 必須加上「參考資訊／非正式固定價目」標示 |
| 神明・祖先 NT$8,000 起 | 顯示「起始參考價格，實際依案件內容與服務範圍確認」，不可自動加價 |
| 其他服務價格未定 | 其他擇日需求與其他服務諮詢一律用「依個案確認」，不能虛構數字 |
| 宜蘭與外縣市到場 | 使用「依案件需求確認」；不得畫出固定服務範圍、行政區或加價表 |
| 各服務交付方向 | 只用「實際服務內容與提供方式於案件確認時說明」；不承諾紙本、PDF、LINE、郵寄或固定數量 |
| 服務處理時間 | 使用「依服務內容、資料完整度與老師安排確認」；不畫 SLA、倒數或預估天數 |
| LINE／電話聯繫偏好 | 兩者並列，不預設哪一個優先；不承諾回覆時間 |
| Trust Strategy：Local + Human + Transparent | 以服務流程、真人工確認、費用事前說明與真實素材 placeholder 表達 |
| 服務卡優先層級 | 可突出婚嫁、入宅／搬遷、新生兒，但不能標成熱銷／最多人選 |
| 婚嫁與其他服務的專業資料 | 可作 Optional Candidate Fields；不可稱為「必填命理資料」 |

### D. 非 UI 功能，但 UI 不得違反的 MVP 技術邊界

- 表單申請資料預計寫入私有 Google Sheet，透過 Google Apps Script 接收；Email 僅可作新申請通知，不是唯一資料庫。

- Google Sheet 的初始案件狀態為 `New／待確認`；這是內部狀態，不需暴露為使用者後台。
- 公開表單的防機器人、防濫用與資料治理仍是正式上線前必做，不可以設計稿假裝已完成。

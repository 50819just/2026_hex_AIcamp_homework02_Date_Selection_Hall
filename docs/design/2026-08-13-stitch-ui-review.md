## 總結論

目前 Stitch UI 整體狀態為：**需修改**

主因不是單一文案小錯，而是以下幾類問題同時存在：

1. 首頁／服務詳情／價格／預約的資訊架構尚未完整對齊 Spec。
2. RWD 只完成部分 Desktop 與部分 Mobile，**Tablet 缺漏**。
3. Booking 雖有 Desktop 4-step 雛形，但 **Mobile 不是 4-step**，且缺少 submitted / error / consent 等關鍵狀態。
4. 前台內容出現多處 **超出已確認事實的補寫**，包含價格、付款流程、交付形式、時程、傳承敘事與高風險素材。

## 1. 首頁、服務詳情、價格、預約頁的資訊架構

### 1.1 首頁
**狀態：需修改**

#### 目前已做到
- Header
- Hero
- 基本 Trust cards
- 部分 Services cards
- Final CTA

#### 主要問題
- Header 導覽未完整對齊 Spec，缺少：
  - `價格說明`
  - `關於我們`
- 首頁主線未完整呈現 Spec 要求的：
  - `How It Works`
  - `Pricing Preview`
  - `On-site Service / Service Area`
  - `About / Trust Preview`
  - `FAQ Preview`
- 首頁目前不是以 `Understand → Service → Trust → Process → Price → FAQ → Action` 的完整結構呈現。

#### 需要修正的內容／文案方向
- 回到「先理解服務、再建立信任、再導向預約申請」的結構。
- 不要把 trust 文案寫得像已確認的品牌主張或營運承諾。
- 首頁應強化：
  - 網站不自動產生擇日結果
  - 實際服務由老師人工確認
  - 價格先提供方向，細節後續確認
  - `開始預約` 導向 `/booking`

#### 本次看到的偏移例子
- `拒絕套版公式，每一筆需求皆由專業老師親自核對八字與時辰。`
- `公開透明的潤金制度`
- `隨時解答您對擇日的疑問與擔憂`

以上文案語氣都比目前 Spec 可支持範圍更重，需收斂為保守版本。

---

### 1.2 婚嫁擇日服務詳情頁
**狀態：需修改**

#### 目前已做到
- 有共用模板雛形
- 有 breadcrumb / hero / 適合情境 / 準備資料 / 流程

#### 主要問題
- 內容已經偏成「固定承諾型服務頁」，超出目前可確認內容。
- 直接補入未確認資料，包含：
  - `雙方父母的出生年月日時`
  - `完成付款`
  - `約需 3-5 個工作天`
  - `提供電子與實體紅紙吉課`

#### 與 Spec 不符處
- 服務流程不應寫成固定付款與固定交付。
- 不應先承諾固定完成天數。
- 不應先寫死交付物為紙本／電子檔／吉課。
- 首次送出資料應維持 minimum required + optional candidate fields 的方向。

#### 修正方向
- 改回「先提出需求 → 補充資料 → 老師確認是否可承接 → 確認費用與安排 → 完成服務」。
- 交付物統一改回：
  - `實際服務內容與提供方式於案件確認時說明。`
- 時程改回：
  - `依服務內容、資料完整度與老師安排確認。`

---

### 1.3 價格說明頁
**狀態：需修改**

#### 主要問題
目前價格頁已經變成接近正式價目表，直接出現：

- `NT$ 3,600 起`
- `NT$ 6,000 起`
- `NT$ 8,000 起`

且服務分類也偏離目前 MVP Spec，例如：
- 開市動土
- 剖腹擇日
- 喪葬晉塔

#### 與 Spec 不符處
- 價格頁應採：
  - 婚嫁：可用參考區間
  - 多數其他服務：`依個案確認`
  - 特殊案件：不自動計價
- 目前不應做成正式固定價目表。
- 不應自行擴寫多個尚未確認的服務分類與定價。

#### 修正方向
- 回到 `Pricing Cards + Pricing Rules`。
- 婚嫁可先保留 `NT$1,500～2,500`，但必須標示為參考資訊。
- 其餘服務以 `依個案確認` 為主。
- 補上「外縣市 / 到場 / 多地點 / 特殊案件不進行網站自動計價」。

---

### 1.4 預約申請頁
**狀態：需修改**

#### Desktop 目前已做到
- 有 breadcrumb
- 有 `開始預約`
- 有 4-step stepper 外觀：
  1. 您的需求
  2. 服務相關資料
  3. 聯絡與到場
  4. 確認並送出

#### 主要問題
- 內容欄位還沒對齊 Spec。
- 服務分類不一致，目前出現：
  - `嫁娶擇日`
  - `入宅安香`
  - `開業開市`
  - `其他擇日`
- 看不到以下 Spec 必要內容：
  - `LINE ID`
  - `希望聯絡方式`
  - `聯絡人姓名`
  - `手機號碼`
  - `所在縣市`
  - 到場條件欄位
  - `資料使用說明`
  - 必勾 consent checkbox
  - review / submit 狀態
  - 送出失敗 state

#### Mobile 主要問題
- 目前 Mobile 只有 3 steps：
  1. 服務項目
  2. 基本資料
  3. 確認預約
- 不符合 Spec 要求的 4-step Booking Flow。

#### 修正方向
- Desktop / Mobile 都回到同一套 4-step：
  1. Need / Event
  2. Service-specific Information
  3. Contact / On-site
  4. Review / Submit
- Mobile 可用 compact step indicator，但不能減成 3-step。
- Step 4 必須補齊：
  - `資料使用說明`
  - 必勾 checkbox
  - `送出預約申請`
  - `返回修改`

## 4. 是否誤做自動算命、線上付款、固定訂金

### 4.1 自動算命
**狀態：需修改**

#### 觀察
- 目前沒有看到「使用者輸入資料後立刻自動輸出吉日結果」的互動 UI。
- 但整體文案與頁面定位，已明顯往「直接擇日／直接提供結果」偏移。

#### 偏移例子
- `專業推算`
- `老師依據八字與通書，進行嚴謹的排盤推算`
- `交付吉課`
- `提供詳細的擇日報告`

#### 修正方向
- 回到「網站提供服務理解 + 預約申請 + 後續人工確認」。
- 不把前台敘事寫成結果即將直接產出。

---

### 4.2 線上付款
**狀態：需修改**

#### 觀察
- 未看到 checkout、刷卡、付款按鈕或線上交易流程。
- 但服務詳情已寫出：
  - `完成付款`
  - `支付服務費用確立訂單`

#### 判斷
- 雖未真正做出 checkout UI，但流程邏輯已偏向線上付款前置成立。

#### 修正方向
- 改回：
  - 預約申請
  - 老師人工確認
  - 事前說明費用
  - 雙方確認安排

---

### 4.3 固定訂金
**狀態：需修改**

#### 觀察
- 未直接出現「訂金」字樣。
- 但目前付款被寫成固定流程節點，容易被理解為固定前置付費。

#### 修正方向
- 不預設所有案件都有付款前置。
- 不預設固定訂金。
- 所有費用安排回到人工確認後說明。

## 5. 是否亂補老師資料、價格、地址、電話、LINE、評價或假照片

### 5.1 明顯亂補／過度承諾內容
**狀態：需修改**

本次看到的高風險補寫包含：

- `百年傳承`
- `傳承古法`
- `傳承正統擇日學理`
- `大師擇日`
- `1-2 個工作天內主動與您聯繫`
- `約需 3-5 個工作天進行推算`
- `提供電子與實體紅紙吉課`
- 多組固定價格

以上都超出目前 Confirmed / Proxy Assumption 可安全呈現的範圍。

### 5.2 聯絡資料
**狀態：需修改**

#### 觀察
- 雖未直接補上實際電話號碼與 LINE ID。
- 但已使用：
  - `LINE 客服`
  - `電話諮詢`

#### 判斷
- 目前更安全的做法仍應保留 placeholder 或保守聯絡入口，不應讓前台看起來像所有聯絡資訊都已正式確認。

### 5.3 評價與資歷
**狀態：符合（避免直接虛構）／但文案仍需收斂**

#### 觀察
- 本次未看到具體客戶評價、星等或假案例。
- 但已出現傳承、專業、大師等過度權威化敘事。

#### 判斷
- 沒直接造假評價，但仍有「資歷感亂補」問題。

### 5.4 照片／素材
**狀態：需修改**

#### 觀察
- 畫面中使用了室內空間照、儀式感照片等素材。
- 目前無法從 Stitch 畫面證明這些是已授權且真實可公開的玄機堂素材。

#### 判斷
- 在未確認素材來源前，屬高風險內容。

#### 修正方向
- 第一版優先改為：
  - 抽象文化圖形
  - 紙張／建築線條／印章感圖形
  - 明確 placeholder

## 建議修正優先順序

### P0 必修
1. 移除或改寫所有未確認的價格、付款、時程、交付物、傳承／大師敘事。
2. Booking Mobile 改回 4-step。
3. 補出 submitted state，文案固定為：`預約申請已送出`。
4. 補齊：
   - `資料使用說明`
   - 必勾 consent checkbox
   - review state
   - error state
5. 補 Tablet 與缺失的 Mobile screens。

### P1 重要
1. 首頁補齊完整 IA 主線。
2. 價格頁改回混合揭露，不做正式價目表。
3. 服務分類統一回 Spec 的六大分類。
4. 導覽與命名統一，例如：
   - `擇日舘` / `擇日館`
   - `婚嫁擇日` / `嫁娶擇日`
   - `入宅・搬遷擇日` / `入宅安香`

### P2 可改善
1. 視覺素材改為更明確的抽象 editorial 方向。
2. Trust 區塊文案更保守、更貼近「人工確認 / 事前說明 / 依需求安排 / LINE／電話聯繫」四原則。

## 最終判定

本次 Stitch UI 可作為第一版視覺探索參考，但**尚未達到可直接對照 Spec 實作的穩定狀態**。

判定如下：

- 首頁：**需修改**
- 服務詳情：**需修改**
- 價格頁：**需修改**
- 預約頁：**需修改**
- Tablet：**缺漏**
- Submitted state：**缺漏**

因此本輪建議先做 **Stitch UI 修正**，再進入 React 對稿；不要直接拿目前這版當實作定稿。

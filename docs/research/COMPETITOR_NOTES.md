# Competitor Notes

## 對象
- 明安堂
- 柯炳榮擇日老祖館
- 沈連官擇日館／大師算算
- 科技紫微 Click108
- 曾定理擇日命卜館

本文件只記錄 UX、表單與服務呈現的參考觀察，不代表玄機堂採用相同命理規則、價格或營運方式。

## 叔叔代理版的使用邊界

- 依玄機堂既有訪談、台灣民俗服務常見情境與競品研究整理的內容，標記為 `Proxy Assumption`。
- Proxy Assumption 可支援 IA、Page Structure、Booking Structure 與 Stitch UI Foundation。
- 實際交付格式、老師公開資料、正式價格、回覆時間、資料保存與專業必填欄位，仍須標記為 `Pending Owner Validation`，不得轉寫成「老師本人已確認」。

## 不可直接複製為玄機堂宣稱

- 競品的年資、傳承、門派、證照、成立年份、評價、固定名字數量、命狀版本、固定價格、營業時間與回覆 SLA 都只是 Research Reference。
- 即使競品使用「一甲子」、「三代」等用語，也不能推定玄機堂具有相同資歷；未取得可驗證資料前，不得寫入玄機堂的主標、Trust、About、服務卡或 FAQ。

## 做得好的地方
- 服務分類與情境說明可作為降低理解門檻的參考。
- 婚嫁與命名類服務常收集比姓名／電話更完整的資料，可作為玄機堂候選欄位來源。
- 部分服務會要求日期區間或候選期間，而不是讓使用者自行判定唯一吉日。
- 到場服務與一般線上／人工服務可以分開呈現。
- 多數競品會同時提供電話、LINE 或其他聯絡渠道，並在人工確認後完成後續安排。
- 部分競品公開固定價格、預約時間或付款方式，可作為資訊透明度的研究參考。

## 可借鏡的流程
- Base Information + Service-specific Information：先收基本資料，再依服務類型顯示欄位。
- Event Date／Desired Period 與 Contact Preference 分開，避免把事件日期誤當成老師預約時段。
- 服務涉及住宅空間時，再詢問地點、到場與交通資訊。
- 網路表單送出後仍由人工聯繫確認，不直接把申請視為正式預約。
- 價格、到場、付款等敏感資訊以清楚狀態說明，避免使用者猜測。
- 將婚嫁、入宅／搬家、新生兒等高辨識度事件放在較前位置，可作為首頁 IA 參考。
- 將住宅搬家擇日與住家／陽宅現場鑑定分開，有助於使用者理解 Event-based 與 Place-based 服務差異。
- 服務頁清楚說明「最後拿到什麼」有助於建立服務價值感，但玄機堂不得直接複製競品的命狀版本、名字數量、紙本格式或解說內容。
- 競品未提供可套用於玄機堂的共同處理天數，因此不建立市場 SLA。
- 部分公開價格資料顯示，老師開始作業後的改名／更改日課可能另行處理；玄機堂只採「依案件進度確認」的原則。
- 真實館址、老師資訊、工作方式與可驗證素材，比抽象的神準／大師形容詞更適合作為信任參考。

## 不足或可改進處
- 不應因競品收集父母生肖、家屬姓名、房屋坐向等資料，就直接視為玄機堂固定必填。
- 不應直接複製競品固定價格、營業時間、付款方式或急件承諾。
- 過度專業的術語不應在第一次表單就要求使用者自行判斷。
- 玄機堂需保留老師人工補問與人工判斷的彈性。

## 競品觀察與玄機堂狀態對照

| 研究觀察 | 玄機堂文件狀態 |
|---|---|
| 婚嫁可能需要雙方出生年月日時 | Proxy Assumption：可作 Conditional Optional Fields 候選 |
| 家屬生肖、房屋坐向、親屬姓名 | Pending Owner Validation，不可直接設為必填 |
| 日期區間／候選日期 | Confirmed MVP Product Decision：使用希望辦理期間 |
| 現場與線上服務分流 | MVP Decision：到場欄位依服務類型條件顯示 |
| 固定價格與線上付款 | Research Reference，不代表玄機堂採用 |
| 營業時間與回覆 SLA | Pending，不能複製競品資料 |
| 首頁主要事件排序 | Proxy Assumption，不代表玄機堂熱門或成交排名 |
| 神明／祖先專業術語 | Candidate Internal Taxonomy / Pending Owner Validation |
| 申請送出與案件成立 | 分為 Booking Request 與 Confirmed Case / Appointment |

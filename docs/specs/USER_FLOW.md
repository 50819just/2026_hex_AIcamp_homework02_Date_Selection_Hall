## 文件目的

本文件用於描述玄機堂擇日舘網站第一版的主要使用者旅程，整理使用者從進站、理解服務、建立信任，到提交預約需求的核心流程與可能阻力，作為頁面規劃與文案設計依據。

## 流程總覽

第一版主要使用者流程可整理為：

1. 進入網站
2. 理解品牌與服務範圍
3. 比較服務內容與價格資訊
4. 建立信任與消除疑慮
5. 提交預約需求
6. 等待人工聯繫與後續確認

### 目前 CTA 層級
- Primary CTA：開始預約／提交預約申請，導向獨立 `/booking` Booking Page。
- 特定服務 CTA 可預選服務類型；使用者進入 Booking Page 後仍可修改。
- Secondary Contact Channel：LINE 詢問、電話詢問；兩者暫不指定優先順序，作為先諮詢的 Secondary Flow。
- MVP 不建立第二張諮詢 Form；正式資料收集只使用統一的預約申請表單。

### 預約資料結構
- 先收集 Base Information，再依服務分類顯示 `Conditional Optional Fields`。
- 不使用所有服務共用的一張超長表單；第一次申請不將專業資料設為 Required。
- 若涉及到場，所在縣市／地區必填，完整地址可於人工確認後再補。
- MVP 資料流暫採網站表單 → Google Apps Script → 私有 Google Sheet；Email 可作新申請通知，LINE／電話維持人工聯絡。
- 日期需求使用「希望辦理期間／候選日期」，與「方便聯絡時間」分開。

### 首頁服務優先層級（Proxy Assumption）
- 第一層：婚嫁、入宅／搬遷、新生兒。
- 第二層：神明／祖先、宅事／到場。
- 第三層：其他擇日需求。
- 此為使用者辨識度與市場參考所形成的資訊架構假設，不代表實際熱門或成交排名。

### Homepage Mainline（Confirmed MVP Product / UX Decision）
- `Understand → Service → Trust → Process → Price → FAQ → Action`
- 使用者應依序理解：玄機堂是什麼、自己屬於哪項服務、為何可以信任、如何處理、大概費用與如何開始。

## 主要流程

### 1. 進入產品
可能入口：
- 首頁直接進站
- 來自社群連結
- 來自訊息分享或熟人介紹
- 來自搜尋結果

使用者目標：
- 快速理解這是什麼網站
- 確認是否有提供自己需要的擇日服務

可能疑慮：
- 這是什麼類型的服務？
- 看起來是否可信？
- 會不會太玄、太模糊、看不懂？

需要對應內容：
- 清楚的首頁主標與副標
- 服務摘要
- 簡單明確的品牌定位說明

### 2. 探索內容或功能
使用者會進一步查看：
- 服務介紹
- 價格資訊
- FAQ
- 關於品牌或老師／顧問介紹

使用者目標：
- 理解各服務的差異
- 知道自己大概屬於哪一類需求
- 確認要準備哪些資料

可能疑慮：
- 不知道該選哪一種服務
- 價格不透明
- 不知道網站只是介紹，還是真的可預約

需要對應內容：
- 清楚分類的服務頁
- 價格頁或價格摘要區塊
- FAQ 補充說明
- 明顯但不壓迫的 CTA

### 3. 完成主要任務
主要任務是提交預約需求表單。

使用者目標：
- 找到預約入口
- 順利填完表單
- 知道送出後會發生什麼事

可能疑慮：
- 表單太長或要填太多
- 不知道資料不完整能不能送
- 不知道送出後會不會有人回覆

需要對應內容：
- 預約按鈕清楚可見
- 送出前有清楚的資料使用 Checkbox 與資料使用說明入口
- 表單欄位說明清楚
- 必填與非必填標示清楚
- 依服務類型顯示不同欄位，降低一次填寫過多資料的負擔
- 到場欄位只在入宅／搬遷、神明／祖先與宅事等適用服務中出現
- 送出後回應文案明確

### 4. 看到結果或下一步
表單送出後，使用者會進入等待人工聯繫的階段。

使用者目標：
- 知道自己已成功送出
- 知道後續等待什麼
- 知道若有補件需求會如何處理

可能疑慮：
- 不知道多久會回覆
- 不知道該用哪個管道聯絡
- 不知道預約是否已正式成立

需要對應內容：
- 「預約申請已送出」訊息，不宣稱預約成功
- 後續流程說明：資料將進入私有結構化預約紀錄，再由人工確認
- 回覆方式（LINE／電話並列）；說明老師會確認資料與服務需求後聯繫，但不承諾固定 SLA

### 首頁區塊任務
- Header：全站導覽與主要 CTA。
- Hero：幾秒內說明人工擇日與相關傳統服務。
- Service Entry：協助使用者判斷自己的事件是否屬於服務範圍。
- Trust／About Preview：展示真實工作方式與可驗證信任內容。
- How It Works：降低第一次預約的不確定感。
- Pricing Preview：呈現代表服務的價格狀態與人工報價原則。
- On-site／Service Area：說明宜蘭、外縣市與到場人工確認。
- FAQ Preview：處理送出前疑問。
- Final CTA／Contact：收斂到開始預約、LINE 或電話。

## 分支流程

### A. 先看 FAQ 再決定是否預約
適用於對服務流程、價格或專業邊界有疑慮的使用者。

### B. 先看關於頁再決定是否預約
適用於對品牌信任度敏感、想了解背景與服務方式的使用者。

### C. 先看價格再決定是否繼續
適用於價格敏感型使用者。

## 錯誤與例外流程

- 找不到適合的服務：需提供聯繫或諮詢導向。
- 表單送出失敗：需有錯誤提示與再次送出機制。
- 資料不足：由人工補問。
- 需求超出第一版服務範圍：需委婉說明無法承接或需另行確認。
- 到場、外縣市、多地點：由人工確認是否承接、交通與費用。
- 入宅／搬遷與宅事／到場同時發生：保留一個主要服務，另加到場需求，不要求使用者提交兩張申請。
- 送出後的 Booking Request 與老師確認後的 Confirmed Case / Appointment 必須分開表達。

## 頁面對應

- 首頁：建立第一印象與主要導流
- 服務頁：協助理解服務差異
- 價格頁：降低價格不透明疑慮
- FAQ 頁：降低流程與邊界疑慮
- 關於頁：建立信任感
- 預約頁：完成表單送出

## 驗收重點

- 使用者能在首頁快速理解網站用途。
- 使用者能在 2 至 3 次頁面跳轉內找到預約入口。
- 使用者能理解送出表單後仍需人工確認。
- 主要疑慮可透過價格頁、FAQ 與關於頁被有效降低。

## 開放問題

- 主要導流來源會是社群、搜尋，還是熟人介紹？
- 首頁是否要直接放價格摘要？
- 是否要提供「先諮詢」與「正式預約」兩種入口？
- 預約申請後的主要聯絡渠道與回覆時間。
- 服務表單是否依服務類型顯示不同欄位。
- 各服務候選欄位中，哪些是真正必要資料。
- 神明／祖先服務的實際子類型與補問順序。

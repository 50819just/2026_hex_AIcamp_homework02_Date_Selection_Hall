## 文件目的

本文件用於定義「擇日館網站更新-專案」的產品範圍、定位、目標使用者、MVP 邊界與成功條件，作為後續服務規劃、內容撰寫、頁面設計與預約流程設計的基礎依據。

## 專案基本資訊

- 專案名稱：擇日館網站更新-專案
- 品牌名稱：玄機堂擇日舘
- 產品類型：擇日服務預約網站
- 產品階段：第一版 MVP 規劃
- 主要目的：建立可被理解、可被信任、可提交需求的服務型網站

## 產品目標

- 清楚介紹玄機堂擇日舘提供的擇日服務內容。
- 建立使用者對品牌、服務流程與專業性的基本信任。
- 讓使用者能理解服務差異、價格方式與準備資料。
- 提供簡單明確的預約入口，讓有需求的使用者能順利送出表單。
- 以網站作為品牌對外的正式資訊窗口，而非僅依賴私人訊息說明。

## 產品定位

本產品定位為一個以東方傳統文化脈絡為基礎的擇日服務預約網站，重點在於服務介紹、信任建立與預約轉換。

本產品不是命理自助工具，也不是娛樂化算命網站，而是以資訊整理清楚、流程說明清楚、需求收集清楚為核心的服務型網站。

## 產品會做的事

- 展示品牌定位與服務理念。
- 介紹各類擇日服務項目。
- 說明服務適用情境、所需資料與交付方式。
- 呈現價格區間或報價原則。
- 提供預約／諮詢表單。
- 告知送出表單後的處理流程。
- 提供常見問題說明。
- 提供聯絡方式與人工確認入口。
- 建立使用者對服務流程的基本安心感。

### MVP 主要服務分類
- 婚嫁擇日
- 新生兒命狀・命名
- 入宅・搬遷擇日
- 神明・祖先事宜
- 宅事・到場諮詢
- 其他擇日需求

首頁維持上述六項主要分類。婚嫁的結婚、訂婚／文定與其他婚嫁需求，於服務詳情或預約表單中再細分，不在首頁拆成多張 Service Card。

### 首頁服務資訊層級（IA／UX Assumption）
- 第一層主要人生事件：婚嫁擇日、入宅・搬遷擇日、新生兒命狀・命名。
- 第二層專業／在地服務：神明・祖先事宜、宅事・到場諮詢。
- 第三層承接入口：其他擇日需求。
- 此排序是依使用者辨識度與市場共通性提出的 IA 假設，不代表玄機堂實際詢問量、成交量或商業優先級排名。

## 產品不做的事

- 不自動生成八字、命盤、黃曆等專業判斷結果。
- 不提供即時演算式命理結果頁面。
- 不承諾絕對結果或保證吉凶成效。
- 不以娛樂化、神祕化、誇張化方式包裝服務。
- 不提供會員系統。
- 不提供後台自助查詢系統。
- 不提供自動排程選時段功能。
- 第一版不包含線上付款。
- 不以大量文章站作為第一版核心。

## 目標使用者

### 主要使用者
- 有婚嫁擇日需求的華語使用者。
- 有婚嫁、新生兒命狀／命名、入宅／搬遷、神明／祖先、宅事或其他擇日需求的使用者。
- 重視傳統禮俗文化與流程說明的人。
- 希望先了解服務內容、資料需求與價格範圍，再決定是否預約的人。

### 使用者特徵
- 對服務專業度與可信度敏感。
- 對流程是否麻煩、價格是否透明有疑慮。
- 可能對命理術語不熟，需要清楚好懂的說明。
- 偏好能先透過網站理解服務，再進入人工聯繫。

### 使用者核心需求
- 快速理解可提供哪些擇日服務。
- 知道每項服務需要準備什麼資料。
- 知道價格如何計算或揭露。
- 知道預約後會發生什麼事。
- 感受到品牌穩定、可信、專業而不浮誇。

## MVP 範圍

### 第一版必備內容
- 首頁
- 服務介紹頁
- 價格／方案說明頁
- 預約流程說明
- 預約表單頁
- 品牌／顧問介紹頁
- FAQ 頁
- 聯絡方式資訊

### 第一版可延後內容
- 線上付款
- 會員登入
- 自動命理演算
- 即時可預約時段選擇
- 後台管理功能
- 大量文章內容區
- 多語系版本
- 自動化客服流程

## 預約模式

第一版預約模式以「使用者填寫表單後，由人工聯繫確認」為主。

流程原則如下：
1. 使用者先透過網站閱讀服務資訊。
2. 使用者提交需求表單。
3. 品牌端人工確認資料是否完整。
4. 暫透過 LINE 或電話與使用者聯繫，主要渠道尚待確認。
5. 確認服務內容、資料、費用與後續安排。

### 案件狀態邊界
- 網站送出後的狀態是 `Booking Request`，代表需求已提交，不代表案件成立。
- 老師完成需求、資料、承接、費用與日期／安排確認後，才進入 `Confirmed Case / Appointment`。
- `申請已送出`、`待人工確認`、`待補資料`、`已確認`、`無法承接／另行說明` 可作為 MVP 內部／流程狀態候選；完整案件追蹤頁不在本階段必做。

此模式可降低第一版系統複雜度，也能保留專業服務需要人工判讀與確認的彈性。

## 產品核心價值

- 讓擇日服務更清楚，不必靠私訊慢慢問。
- 讓使用者在接觸服務前就能理解流程與準備事項。
- 用穩重、可信、好懂的方式呈現傳統文化服務。
- 讓專業判斷保留在人與人的確認中，而不是交給系統亂算。
- 讓品牌有一個正式、可持續更新的網站入口。

## Homepage Product / UX Decision

此節屬 MVP Product / UX Decision，不等同於玄機堂老師的命理專業規則：

- 首頁主線：`Understand → Service → Trust → Process → Price → FAQ → Action`。
- 首頁依序傳達品牌用途、服務分類、信任方式、處理流程、價格原則與開始方式。
- Hero 只需讓使用者理解玄機堂提供人工擇日與相關傳統服務，不在首屏展開完整命理教育。
- 首頁服務視覺層級暫採：婚嫁／入宅／新生兒為第一層；神明／祖先與宅事／到場為第二層；其他需求為第三層。
- Header 導覽暫含首頁、服務項目、價格說明、關於玄機堂、常見問題，並保留「開始預約」Primary CTA。
- 所有主要「開始預約」CTA 導向獨立 `/booking`；首頁不嵌入完整預約表單。特定服務 CTA 可預選服務，但使用者進入後仍可修改。
- LINE 與電話保留為 Secondary Contact，Mobile 可收進 Menu，但「開始預約」需保持容易找到。

## 成功條件

- 使用者能看懂網站主要提供哪些服務。
- 使用者能理解各服務的基本差異。
- 使用者能找到價格資訊或報價原則。
- 使用者能順利送出預約表單。
- 使用者知道送出後下一步會怎麼進行。
- 網站整體呈現出可信、穩定、清楚的品牌形象。

## UI Foundation Batch（MVP Product / UX Decision）

第一批設計驗證範圍暫定為：

1. Home
2. Service Detail Template（代表服務先使用婚嫁擇日）
3. Booking
4. Pricing
5. Services Listing
6. About
7. FAQ / Contact

Home、Service Detail Template、Booking、Pricing 是最優先的 Stitch Foundation，並至少提供 Home Mobile 與 Booking Mobile。Services Listing、About、FAQ / Contact 依上述順序續作；Error、Admin、Account 與 Checkout 不列入本階段。

## 假設

- 第一版以台灣繁體中文使用者為主要對象，其他華語地區待後續確認。
- 服務成交前仍需人工確認資料與需求，不依賴系統自動判斷。
- 各服務可先以區間價格或起始價格呈現，而非一開始就公開完整精算表。

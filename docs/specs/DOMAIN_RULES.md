# DOMAIN_RULES.md

狀態：draft  
最後更新：2026-08-13

## 文件目的

本文件用於定義玄機堂擇日舘網站在內容語氣、專業邊界、可用說法與風險控管上的規則，避免網站文案偏向娛樂化、誇張化或超出專業服務可承諾的範圍。

## 語氣方向

- 穩重
- 清楚
- 有文化感
- 不玄虛
- 不娛樂化
- 有禮但不過度神祕

## 建議使用說法

- 擇日建議
- 禮俗諮詢
- 服務流程說明
- 人工確認
- 依需求提供建議
- 適用情境
- 注意事項

## 避免使用說法

- 絕對保證
- 一定大吉
- 系統自動算出最佳命運結果
- 娛樂化算命、神準預言等誇張字眼
- 暗示只要購買服務就必然改變人生結果的說法

## 專業邊界

- 網站不自動生成八字、命盤、黃曆等專業判斷結果。
- 網站的角色是資訊整理、服務介紹與需求收集，不取代人工專業判讀。
- 涉及個別命理判斷的內容，以人工確認結果為準。
- 不宣稱服務具備保證性成果。

## 內容原則

- 以清楚說明服務內容與流程為優先。
- 對有不確定性的內容，使用保守表述。
- 對專業術語需搭配白話說明，降低理解門檻。
- 在品牌文化感與一般使用者可理解之間取得平衡。

## 風險提示原則

- 若某項服務需視個案條件判定，應明確註記由人工確認。
- 若價格、時程或交付形式尚未完全固定，應保留待確認標記。
- 涉及退款、改期、交付時程等敏感資訊，需與對應 spec 保持一致。

## 價格與付款說法

- 未確認正式價格時，不得使用「固定價」或暗示所有案件適用同一金額。
- 婚嫁 NT$1,500～2,500 僅能標示為 MVP 參考區間／Mock Reference Price。
- 其他服務、外縣市、到場、多地點與神明／祖先特殊案件，應說明為人工確認或依個案報價。
- 可說明諮詢費、車馬費等費用會在服務前先確認；不得自行宣稱所有案件必須先付訂金。
- 尚未確認的付款方式、特殊案件先收費條件與改期／退款規則，應標示待確認。

## 預約資料與回覆說法

- 預約資料只可用於預約聯繫、服務確認與相關溝通；不得寫成可公開展示、作案例或作其他未說明用途。
- 表單送出前使用明確、必勾的資料使用 Checkbox，不使用「我同意所有條款與服務」等過度籠統說法。
- 建議 Checkbox 文案：「我同意玄機堂擇日舘使用本次填寫資料，作為預約聯繫、服務確認與相關溝通之用。」
- 需提供「了解資料使用說明」入口，但未確認前不自行補造完整法律條款、保存期限或刪除政策。
- 送出後可說：「預約申請送出後，老師將確認您提供的資料與服務需求，並透過 LINE 或電話與您聯繫。」
- 使用「老師將確認您提供的資料與服務需求，並透過 LINE 或電話與您聯繫」，不得使用 24 小時內、當日、一個工作日、即時或「儘快」等回覆承諾。

## 表單與日期用語

- 使用「希望辦理期間」、「候選日期」或「尚未確定，希望老師協助」等說法。
- 不使用「選擇吉日」、「系統推薦最佳日期」等會讓人誤以為網站自動擇日的說法。
- 「方便聯絡時間」是聯絡偏好，不是正式預約時段，也不代表老師承諾該時段一定有空。
- 競品出現的出生資料、家屬生肖、房屋坐向、親屬姓名等，只能作為候選欄位來源；未經業主確認不得寫成玄機堂固定必填。

## 到場服務說法

- 到場欄位依服務類型條件顯示，優先適用於入宅／搬遷、神明／祖先與宅事／到場諮詢。
- 婚嫁、新生兒命狀與命名不預設一定需要老師到場；特殊需求可放在其他需求說明。
- 外縣市或跨區到場可使用：「可先提供地點與服務內容，老師確認後將與您說明安排及相關費用。」
- 不使用自動公里數計價、固定每公里車馬費或自動判斷是否承接的說法。

## 神明／祖先服務用語

- 前台優先使用白話分類：「神明相關」、「祖先牌位相關」、「搬家／入宅相關」、「其他」、「不確定，希望老師協助確認」。
- 「合爐」、「退神」、「晉塔」、「安神位」、「公媽龕」等術語可留在內部候選 taxonomy，但不要求第一次申請的使用者自行判斷。

## 服務分類用語

- 「入宅／搬遷擇日」描述的是事件：使用者要搬家、入住或安排一個日期，屬 Event-based Service。
- 「宅事／到場諮詢」描述的是空間：使用者希望老師查看房屋、位置或宅事，屬 Place-based Consultation。
- 若兩者同時存在，以主要服務搭配額外需求說明，不要求使用者下兩張申請。

## 案件狀態用語

- 網站送出後使用 `Booking Request／預約申請`，不可稱為正式案件或已成立預約。
- 老師確認服務範圍、資料、費用與日期／安排後，才可使用 `Confirmed Case / Appointment／正式預約／案件成立`。
- 可使用「尚需補充資料，老師將與您聯繫確認」，不要使用「預約失敗」描述資料不足。

## 交付與時程說法

- 每項服務可規劃交付類型與方式欄位，但未經業主確認前，不得承諾固定紙本、電子檔、LINE 圖片、電話解說、郵寄、到館領取或固定數量的命名結果。
- 服務時間使用：「實際處理時間會依服務內容、資料完整度與老師安排而有所不同，確認案件時將一併說明。」
- 不使用「24 小時完成」、「3 個工作天」、「7 天交付」等未確認時程。
- 急件只能描述為時間需求訊號，不得寫成保證優先或保證承接。
- 修改／改期需依案件進度人工確認，不使用「免費修改」、「無限次更改」等未確認承諾。

## Trust 內容原則

- Trust 優先使用 Local + Human + Transparent：真實老師、真實服務空間、真實工作方式與清楚流程。
- 只有業主提供且可驗證的資料，才能公開老師稱謂、經歷、成立年份、傳承、館址、照片、案例或評價。
- 不假造歷史、資歷、客戶見證、評分、案例或任何會被理解為真實品牌證據的 AI 圖像。
- MVP Demo 可使用 AI 生成的「示意人物」與「示範個案」；必須明確標示、不可搭配真實姓名或評價語氣，亦不可被表述為玄機堂的實際老師、客戶、服務紀錄或店面。詳見 `DEMO_VISUAL_ASSET_SPEC.md`。
- 若尚未取得素材，可先保留 Trust 區塊結構與 Placeholder，不得讓 Placeholder 看起來像正式事實。

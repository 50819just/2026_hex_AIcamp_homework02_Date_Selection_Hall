# BOOKING_FLOW.md

狀態：draft  
最後更新：2026-08-13

## 文件目的

本文件用於定義玄機堂擇日舘網站第一版的預約流程，包含使用者操作步驟、表單欄位、送出後回應、人工確認節點，以及改期／取消等例外情境。

## 預約流程總覽

第一版採用表單送出後，由人工聯繫確認的模式。

1. 使用者瀏覽網站並了解服務內容。
2. 使用者選擇欲預約的服務項目。
3. 使用者填寫需求表單。
4. 系統顯示「預約申請已送出」，不代表預約正式成立。
5. 品牌端人工檢查資料完整度。
6. 暫由老師透過 LINE 或電話聯繫使用者；主要渠道尚未指定。
7. 雙方確認需求、價格、時程與後續安排。
8. 預約正式成立。

### MVP 預約資料接收（Confirmed MVP Product Decision）

```text
使用者填寫 Booking Form
→ 送出預約申請
→ Google Apps Script 將資料寫入私有 Google Sheet
→ 可選擇發送 Email 新申請通知
→ 老師／家人查看申請
→ 人工透過 LINE 或電話聯繫客人
```

- Google Sheet 作為結構化預約紀錄；Email 僅可作通知，不作為唯一案件資料庫。
- LINE 與電話是人工聯絡渠道，不是 Booking Database；第一版不建立 LINE Bot 自動接單、CRM、完整後台、會員系統或複雜資料庫。
- Google Sheet 初始狀態使用 `New／待確認`。欄位只保存網站實際需要的資料，例如 Submitted At、Booking ID、聯絡資料、服務類型、希望辦理期間、地點、到場需求、服務專屬資料、備註與狀態。
- 最終 Google Account、資料管理者與 Email 通知收件人仍為 Pending Owner Validation。


### 費用與付款節點
- 客人通常在服務前先詢問費用。
- 諮詢費、車馬費等相關費用原則上於服務前說明並確認。
- 第一次送出預約申請不付款；老師人工確認服務內容、服務總價與日期／時間後，才建立綠界預約訂金交易。
- 預約訂金級距：服務總價 NT$5,000 以下收 NT$800；NT$5,001～8,000 收 NT$1,200；NT$8,001 以上收 NT$1,600。
- 尾款為服務總價扣除已付訂金；付款成功後需向使用者顯示尾款明細。
- 訂金付款成功不得取代老師人工確認專業內容；若日期／時間或案件成立條件尚未完成，仍保留人工確認狀態。
- 取消、改期、退款、尾款收取時間與實際付款方式仍待確認。

### 表單資料架構

採用 **Base Information + Conditional Service-specific Information**：

1. 先填寫所有服務共用的基本資料。
2. 選擇服務後，再顯示該服務的候選專屬欄位。
3. 送出預約申請。
4. 專業資料不足時，由老師人工補問與確認。

不使用所有服務共用的一張超長表單，也不把所有專業資料都延後到人工詢問。

### 首次送出的最低資料
第一次提交預約申請至少需要：
- 聯絡人姓名
- 手機號碼
- 服務類型
- 需求簡述
- 希望辦理日期／期間
- 所在縣市
- 希望聯絡方式

所有服務專業欄位一律先視為 `Conditional Optional Fields`；若不足以判斷需求，由老師聯繫補問。第一次提交不應要求使用者填完老師可能需要的全部命理或宅事資料。

若需求涉及到場，所在縣市／地區為必填；完整地址可於人工確認後再補。

## 統一申請與先諮詢分流（Confirmed MVP Product Decision）

- MVP 只建立一套「預約申請」表單，不建立獨立的諮詢 Form。
- 使用者若仍在初步詢問階段，使用 LINE／電話 Secondary Flow；此流程不取代網站的結構化預約紀錄。
- 網站表單送出後仍是 `Booking Request`，不因名稱含「預約」就表示正式案件成立。


## Booking Page 入口規則（Confirmed MVP UX Decision）

- 首頁不嵌入完整預約表單；所有主要「開始預約」CTA 導向獨立 `/booking` Booking Page。
- Service Card 可使用 query parameter 或 route state 預選服務，例如 `/booking?service=marriage`。
- 預選值只用於降低填寫負擔，使用者進入後仍可修改服務類型。
- LINE／電話是先諮詢的 Secondary Flow，不取代 Booking Page 的正式資料收集與送出。

## 4-Step Booking UI（Confirmed MVP Product / UX Decision）

資料模型仍可保留五個概念：Service、Event、Professional Data、Contact、Review；但前台不拆成五個過度細碎的畫面。

### Step 1｜您的需求
- 服務類型
- 婚嫁等服務子需求
- 希望辦理期間／候選日期
- 時間較急訊號
- 簡短需求說明

### Step 2｜服務相關資料
- 依服務類型條件顯示專業候選欄位。
- 使用 Progressive Disclosure，不顯示其他服務的欄位。

### Step 3｜聯絡與到場
- 聯絡人姓名、手機、LINE、希望聯絡方式與方便聯絡時間。
- 若服務涉及到場，再顯示地址、所在縣市、多地點、接送與到場備註。

### Step 4｜確認並送出
- 顯示服務、希望辦理時間、主要資料、聯絡方式與到場需求摘要。
- CTA 使用「送出預約申請」，不使用「立即預約成功」。
- 送出前必須勾選資料使用 Checkbox（UI / Content Placeholder）：「我已閱讀資料使用說明，並同意本次填寫資料供玄機堂擇日舘進行預約聯繫、服務確認及相關溝通使用。」未勾選不得送出。
- Checkbox 附近提供 Data Usage Notice、Privacy / Data Notice Link 與 Privacy Contact Entry Point；完整 Privacy Policy 與資料治理細節屬 `Required Before Production Launch / Pending Final Validation`。

Desktop 與 Mobile 共用同一套 4-step 邏輯，差異只在版面、欄位排列、進度指示與間距。

## 使用者操作步驟

### Step 1. 進入網站
- 入口可能來自首頁、服務頁、FAQ 或外部社群導流。
- 使用者需要先快速理解品牌定位與服務範圍。

### Step 2. 閱讀服務資訊
- 使用者瀏覽服務類型、適用情境、資料需求與價格資訊。
- 若仍有疑問，可先看 FAQ 或關於頁建立信任感。

### Step 3. 前往預約表單
- 預約 CTA 應從首頁、服務頁、價格頁、FAQ 等頁面都能到達。
- CTA 文案需清楚，例如「提交預約需求」或「先填資料，由我們與你確認」。

### Step 4. 填寫需求表單
建議欄位如下：
- 姓名
- 手機
- LINE ID 或其他聯絡方式（可選）
- 希望聯絡方式：LINE／電話／皆可
- 需求類型／服務項目
- 簡短需求說明
- 希望辦理期間／候選日期
- 日期需求方式：有希望日期／可接受期間／有候選日期／尚未確定，希望老師協助
- 所在縣市
- 方便聯絡時間（選填）：上午／下午／晚上／皆可／其他
- 補充說明
- 依服務類型顯示的條件式額外欄位

### 日期欄位規則
- 「希望辦理期間」代表 Event Date／Desired Period，不是預約老師的時間。
- 使用者可提供單一希望日期、日期區間、2–3 個候選日期，或選擇尚未確定。
- 不使用「選擇您的吉日」，也不提供系統推薦唯一日期。
- 「方便聯絡時間」屬於 Contact Preference，不代表老師承諾該時段一定有空。

### 服務專屬欄位候選
- 婚嫁：新人姓名、出生日期、出生時間、國曆／農曆、結婚／訂婚／其他／不確定、希望辦理期間。
- 新生兒命狀：新生兒姓名（若已有）、性別、出生年月日時、國曆／農曆、聯絡人與備註。
- 新生兒命名：性別、出生年月日時、國曆／農曆、姓氏、偏好字與避免字。
- 入宅／搬遷：舊址（若適用）、新址、縣市、搬遷期間、是否已入住、是否涉及神明／祖先。
- 神明／祖先：需求類型、原所在地、新所在地、縣市、希望辦理期間與需求說明。
- 以上專業欄位中，未經業主確認的家屬生肖、房屋坐向、親屬姓名等，維持 `Proxy Assumption` 或 `Pending Owner Validation`，不得視為正式必填。

### 神明／祖先前台分類
- 神明相關
- 祖先牌位相關
- 搬家／入宅相關
- 其他
- 不確定，希望老師協助確認
- 合爐、退神、晉塔、安神位、公媽龕等術語不作為第一次申請的必要選項。

### 到場欄位條件
- 入宅／搬遷、神明／祖先與宅事／到場諮詢可顯示「是否希望老師親自到場」。
- 婚嫁、新生兒命狀與命名不預設需要到場；特殊需求可放入其他說明。
- 若使用者選擇需要到場，再顯示縣市／地區（必填）、完整地址（可後補）、多地點與是否方便協助接送等欄位。

### 事件日期與案件聯絡時間
- `Event Date / Desired Period`：希望辦理日期、日期區間或候選日期。
- `Contact Preference`：希望聯絡方式與方便聯絡時間。
- 兩者不可混合；方便聯絡時間不代表正式預約時段。

### Step 5. 送出後回應
- 顯示「預約申請已送出」，不可顯示「預約成功」。
- 告知後續會由人工聯繫確認。
- 提醒使用者留意 LINE 或電話聯繫。
- 不承諾固定回覆 SLA；使用「預約申請送出後，老師將確認您提供的資料與服務需求，並透過 LINE 或電話與您聯繫。」
- 不使用 24 小時內、當日回覆或一個工作日等未確認承諾。

### Step 6. 人工確認
- 確認表單資料是否完整。
- 若資料不足，主動補問。
- 若服務範圍不適用，應委婉說明無法承接或需進一步確認。
- 確認服務內容、服務總價、日期／時間與是否適用訂金級距。

### Step 7. 綠界預約訂金
- 依確認後的服務總價建立 NT$800、NT$1,200 或 NT$1,600 預約訂金交易。
- 交易品名標示為「預約訂金」，不可誤標示為完整服務費。
- 後端確認綠界通知與主動查單結果後，才標記訂金已付款。
- 付款失敗／取消時保留案件資料，不得顯示付款成功或預約成功。

### Step 8. 付款後說明
- 顯示服務總價、已付訂金、尾款與尾款說明。
- 尾款實際收取時間與方式依案件確認結果處理。

## 人工確認節點

- 服務類型是否明確。
- 聯絡方式是否可用。
- 日期需求是否合理。
- 是否涉及複雜情境，需要額外補件。
- 是否需進一步說明價格、改期或退款規則。
- 是否涉及外縣市、多地點、到場或神明／祖先相關特殊案件。
- 是否需要條件式到場欄位：入宅／搬遷、神明／祖先、宅事／到場諮詢優先處理。
- 服務費、諮詢費與車馬費是否需要分開說明。
- 是否需要補充服務所需的出生資料、地址或其他專業資訊。

## 交付形式說法

- 各服務目前只定義 Deliverable Direction，不承諾紙本、電子檔、LINE、電話、到場或任何固定格式。
- 前台統一使用：「實際服務內容與提供方式於案件確認時說明。」
- 個別服務的實際交付內容、方式與完成時間仍由老師於案件確認後說明。


## 處理時間與急件

- 表單可提供「時間較急，希望老師優先確認是否可承接」選項。
- 這只是 Urgency Signal，不代表保證優先處理、一定承接或一定加費。
- 實際處理時間依服務內容、資料完整度、是否需要到場與老師安排確認。
- 不在前台承諾固定完成天數或固定回覆 SLA。

## Case Handling Flow

1. 收到網站、LINE 或電話提出的需求。
2. 確認需求類型與主要事件。
3. 確認基本資料是否足夠，必要時人工補問。
4. 判斷是否屬於服務範圍、日期是否來得及、地點是否可承接。
5. 說明服務方式、諮詢費、車馬費與其他費用。
6. 確認辦理期間、老師處理／到場安排與聯絡方式。
7. 雙方完成確認後，才視為正式預約／案件成立；此成立條件為 `Proxy Assumption`，仍待業主最終確認。
8. 確認服務與日期／安排後，依級距支付預約訂金。
9. 完成服務後依事前約定收取尾款。

### Case Status 候選
- 申請已送出
- 待人工確認
- 待補資料
- 待支付預約訂金
- 預約訂金已付款
- 付款失敗／取消
- 已確認
- 無法承接／另行說明

MVP 前台只需要清楚呈現申請送出與後續人工確認，不需要先做會員式案件追蹤頁。

## 改期流程

- 使用者提出改期需求。
- 人工確認原預約狀態與新需求。
- 依 `PRICING_POLICY.md` 規則判定是否產生改期費。
- 回覆可處理方式與後續安排。
- 老師尚未開始作業前：使用者可盡早聯繫更新聯絡資料、需求、希望日期區間或地址。
- 老師已開始擇日／命名／處理後：若變更日期條件、主要需求、地點或服務內容，可能需要重新處理、重新安排或重新報價。
- 網站不預先承諾免費修改或無限次修改。

## 取消流程

- 使用者主動提出取消。
- 人工確認目前進度。
- 依價格與退款規則說明是否可退費或保留。
- 完成取消通知與紀錄。
- 目前沒有正式取消費、退款比例或免費取消期限，前台維持人工確認說法。

## 錯誤與例外流程

- 表單欄位未填完整：前端提示必填欄位。
- 未勾選資料使用 Checkbox：阻止送出並清楚說明資料使用目的。
- 聯絡資料格式錯誤：前端顯示格式提醒。
- 表單送出期間：顯示 Loading State 並暫時避免重複送出。
- 表單送出失敗：保留已填資料、提供 Retry 與 LINE／電話替代聯繫方式。
- 使用者需求超出服務範圍：送出後由人工說明。
- 使用者重複送單：需有人工識別與整併機制。
- 不使用固定回覆時間承諾、即時、當日、24 小時內或「儘快聯繫」等可能被理解為 SLA 的說法。
- 無法在預期時間內回覆：需有替代說明文案。

## 驗收重點

- 使用者可從主要頁面順利進入預約表單。
- 表單欄位能支撐第一版服務需求收集。
- 送出後有清楚的「預約申請已送出」訊息與後續說明。
- 人工確認節點能覆蓋主要風險與例外情境。

## 待確認事項

- 主要對外聯絡渠道是 LINE 還是電話，以及是否仍保留其他管道。
- 最終由哪個 Google Account 管理 Google Sheet、誰接收 Email 通知，以及是否正式啟用通知。
- 預約資料保存多久，以及後續如何管理或刪除。
- 是否建立 LINE 官方帳號；目前 LINE 僅為人工聯絡渠道。
- 營業時間、休息日與一般回覆時間；目前不承諾固定回覆 SLA。
- 特殊案件是否可能先收訂金或其他費用。
- 實際接受哪些付款方式。
- 是否要加入附件上傳欄位。
- 是否要區分一般諮詢與正式預約。
- 各服務候選專業欄位中，哪些是真正必要資料。
- 神明／祖先服務實際有哪些子類型與補問順序。
- 哪些服務可到場、宜蘭縣內與外縣市如何承接，以及是否涉及接送與多地點。
- 是否有固定營業時間與急件規則。
- 各服務實際交付內容、交付方式與完成時間。
- 急件定義、是否加費與不接受範圍。
- 老師已開始作業後的修改／重選／重新報價規則。
- 取消與退款規則。

# Content Requirements

狀態：draft  
最後更新：2026-08-13

## 文案需求
- 首頁需清楚說明服務定位、七項主要服務分類與人工確認流程。
- 婚嫁首頁維持單一「婚嫁擇日」名稱；婚嫁細項只在服務詳情或預約表單出現。
- 價格文案需區分正式價格、參考區間／Mock Reference Price 與「依個案確認」。
- 諮詢費、車馬費等費用可說明為服務前確認，不得暗示所有案件固定收訂金。
- Trust／About 需要老師／服務者介紹結構，但未確認的個人資料與經歷不得自行補寫。
- LINE 與電話暫時並列呈現，不指定主要聯絡渠道。
- 預約表單需讓使用者理解：先填共同基本資料，再依服務類型補充選填的專業資料；若資料不足，由老師後續補問。
- 網站只有統一的「預約申請」表單；先諮詢使用 LINE／電話 Secondary Flow，不另建諮詢 Form。
- Submit 前需顯示必勾資料使用 Checkbox，UI / Content Placeholder 文案為：「我已閱讀資料使用說明，並同意本次填寫資料供玄機堂擇日舘進行預約聯繫、服務確認及相關溝通使用。」
- Checkbox 附近需提供「了解資料使用說明」入口；本輪只定義入口與用途，不自行補寫完整法律條款。
- 「希望辦理期間」代表事件日期需求；「方便聯絡時間」代表聯絡偏好，兩者需使用不同標籤與說明。
- 到場說明需依服務類型出現，不應讓所有服務都預設需要到場。
- 首頁服務可採分層呈現：婚嫁／入宅／新生兒為主要人生事件，神明／祖先與宅事／到場為專業服務，其他需求作為承接入口；此為 IA 假設，不得寫成熱門排行。
- 神明／祖先前台使用白話分類，避免第一次要求使用者理解合爐、退神、晉塔等術語。
- 入宅／搬遷文案聚焦「安排搬家／入住日期」；宅事／到場文案聚焦「房屋／空間現場確認」。
- 每項服務介紹需預留「交付內容」與「處理時間」說明；交付形式尚未確認時，統一使用「實際服務內容與提供方式於案件確認時說明」，不承諾紙本、電子檔、LINE 或固定格式。
- 交付文案不可直接複製競品的固定紙本格式、命名數量、命狀版本或電子檔承諾。
- Trust 文案優先呈現 Local + Human + Transparent 的真實工作方式，不以抽象神準或大師形容詞取代證據。

## 首頁 CTA 與 Trust 文案需求

- 首頁的主要 CTA 使用「開始預約」並導向獨立 `/booking` Booking Page；首頁不嵌入完整表單。
- 來自特定服務卡的 CTA 可傳遞服務預選值，但 Booking Page 需允許使用者修改服務。
- Trust Section 第一版使用下列真實服務原則，不以空泛的「專業、用心、值得信任」形容詞取代：
  - 老師人工確認：專業判斷不由系統自動生成。
  - 費用事前說明：服務內容及相關費用會先確認清楚。
  - 依實際需求安排：到場、外縣市與特殊案件由人工溝通。
  - LINE／電話聯繫：送出需求後，由老師進一步確認。
- 若有可公開的真實玄機堂招牌或場館照片，可優先放入 Trust Section。
- 競品「一甲子三代」等資歷型標語僅可作內容研究參考；未取得玄機堂真實可驗證資料前，不得轉寫為本品牌主標、Trust 文案或任何前台宣稱。

## 圖像素材需求
- 真實老師照片、工作環境、店面／招牌、案例或評價素材是否可公開，仍待確認。
- MVP Demo 可使用 AI 生成的示意人物、示範個案與裝飾視覺；使用規則以 `docs/specs/DEMO_VISUAL_ASSET_SPEC.md` 為準。
- Demo 人物必須標示「示意人物」或「Demo 示意」，不得冒充已確認老師、真實工作人員或真實客戶。
- Demo 個案必須標示「示範個案」或「情境示例」，不得偽裝成真實客戶評價、五星評分、服務紀錄或公開推薦。
- 可使用紙張、書冊、朱印、木質桌面、日期／日曆等抽象裝飾，但不得製作足以宣稱玄機堂真實傳承、真實老店、真實牌匾、真實證明或真實歷史照片的素材。
- 真實素材取得且公開權限確認後，可逐步替換 Demo 視覺；替換時不得改變既有版面、流程或文案邊界。

## 資料欄位需求
- 基本欄位至少需要姓名、聯絡方式、服務分類、需求說明與日期／期間。
- 到場資訊只在適用服務中顯示。若涉及到場，所在縣市／地區為必填；完整地址可於人工確認後再補，詳細地址格式與欄位規則待確認。
- 婚嫁、新生兒、搬遷與神明／祖先欄位依服務類型提供 Conditional Optional Fields；第一次申請不將專業資料設為必填，改由老師人工補問。
- 共用聯絡欄位可包含希望聯絡方式：LINE／電話／皆可。
- 方便聯絡時間可作選填欄位；附件上傳與地址詳細程度待確認。
- 競品欄位如家屬生肖、房屋坐向、親屬姓名等，需標示為候選需求，不得直接寫成固定必填。
- 第一次送出只要求最低基本資料，專業欄位以選填與人工補問呈現。

## 狀態文案
- 送出後使用：「預約申請已送出」。
- 補充說明：「預約申請送出後，老師將確認您提供的資料與服務需求，並透過 LINE 或電話與您聯繫。」
- 不使用 24 小時內、當日回覆、一個工作日、即時或「儘快」等未確認的回覆承諾。
- 付款說明可使用：「服務內容、費用與付款方式將於正式確認案件時說明，並依雙方事前約定辦理。」
- 急件說明不可承諾一定承接，可使用「時間較急，希望老師確認是否可承接」作需求資訊。
- 時程說明可使用：「實際處理時間會依服務內容、資料完整度與老師安排而有所不同，確認案件時將一併說明。」
- 修改說明可使用：「若需求或資料需要修改，請盡早與老師聯繫……是否需要重新處理或調整費用，將依實際案件確認。」

## Homepage Content Architecture

- Header：導覽與開始預約。
- Hero：人工擇日與相關傳統服務的清楚定位。
- Service Entry：主要人生事件、專業／在地服務與其他需求入口。
- Trust／About Preview：真實工作方式與可驗證信任內容。
- How It Works：四步人工確認流程。
- Pricing Preview：代表服務的價格狀態與人工報價原則。
- On-site／Service Area：宜蘭、外縣市與到場說明。
- FAQ Preview：送出前的主要疑問。
- Final CTA／Contact：開始預約、LINE、電話。
- 不使用：「預約成功」、「系統已為您選定最佳日期」等超出實際流程的說法。
- 案件狀態可依序使用：「申請已送出」、「待人工確認」、「待補資料」、「已確認」、「無法承接／另行說明」。
- 資料不足使用：「尚需補充資料，老師將與您聯繫確認」，不使用「預約失敗」。

## 空狀態／錯誤訊息
- 資料不足時，提示使用者補充可提供的資訊，並保留由老師人工補問的可能。
- 無法判斷服務分類時，提供「其他擇日需求／不確定，希望老師協助確認」。
- 表單送出失敗時，提供重試與 LINE／電話替代聯繫方式，並保留使用者已填資料；正式錯誤文案待確認。
- 送出期間需提供清楚的處理中狀態，避免使用者重複送出。
